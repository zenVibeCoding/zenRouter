## 2. 组织与权限

### 推荐路线：登录复用标准，业务授权独立管理

ZenRouter 作为 OIDC 客户端接企业已有身份服务，Rust 侧可采用 openidconnect 库。需要兼容 LDAP／AD 或 SAML 身份源时，优先评估 Keycloak 桥接；它提供 OIDC、SAML、身份代理和 LDAP 联邦。Keycloak 是可选部署组件，不要求已有合适 SSO 的企业再部署一套。[Keycloak 协议支持](https://www.keycloak.org/securing-apps/overview)、[LDAP 与身份代理](https://www.keycloak.org/docs/latest/server_admin/index.html)、[Rust OIDC 库](https://docs.rs/openidconnect/latest/openidconnect/)。

登录、组织同步和业务授权分别设计。飞书官方提供基于 OAuth 2.0 的网页登录；读取通讯录还受到应用授权和组织可见范围约束。因此保留飞书专用身份／目录连接器，不默认认为“能登录”就能获得完整部门树或立即同步离职状态。[飞书登录](https://open.feishu.cn/document/qr-code-scanning-login-for-web-app/introduction)、[通讯录访问边界](https://open.feishu.cn/document/server-docs/api-call-guide/generic-error-code)。

### 授权技术比较

| 选择 | 已核实能力与技术形态 | 主要代价 | 当前取舍 |
| --- | --- | --- | --- |
| casbin-rs | Rust 授权库；Casbin 支持角色、角色继承与域内 RBAC | 组织范围、数据过滤、策略持久化和多实例更新仍需集成 | 首选验证，适合目前角色与部门作用范围明确的需求 |
| Cedar | Rust 策略引擎；支持 RBAC／ABAC、策略与 schema 校验 | 需要设计实体、上下文和策略语言的管理方式 | 当属性条件与复杂约束明显增加时作为替代方案 |
| OpenFGA | Go 授权服务，通过 API 表达关系、角色和资源权限 | 增加独立服务、关系同步和一致性管理 | 跨团队共享资源与复杂关系授权成为主要需求时再引入 |
| 全部放入身份平台 | 可复用身份平台已有组和角色管理 | 业务资源与身份系统耦合，难统一额度委派、正文权限等语义 | 身份属性可作为输入，业务权限仍由 ZenRouter 定义 |

来源：[casbin-rs](https://github.com/apache/casbin-rs)、[域内 RBAC](https://casbin.apache.org/docs/rbac-with-domains/)、[Cedar](https://docs.cedarpolicy.com/)、[OpenFGA 角色与权限](https://openfga.dev/docs/modeling/roles-and-permissions)。各库提供授权判断基础，并不自动实现我们要求的组织管理产品。

### 需要保留的架构边界

身份源负责证明“是谁”，ZenRouter 管理“在哪些部门和资源上可以做什么”。使用稳定外部身份标识进行绑定，不直接按同名或邮箱自动合并账号。人员身份与应用服务身份分开：员工离职、凭证撤销、应用归属变更分别处理。

以“角色 + 资源作用范围”为首期授权模型，覆盖控制台、管理 API、模型调用、检索、原文查看和导出。部门主管只能委派自己获准委派的范围；企业管理员不天然拥有全部正文读取权。授权引擎不负责金额是否足够，额度模块保留自己的事务约束。

组织与角色关系建议存于 PostgreSQL，授权配置带版本并在实例间同步。登录成功、组同步和权限缓存更新不能当作实时撤权已完成；撤权时限、缓存有效期和身份源不可用时的行为留作验收。可叠加数据库行级安全作为隔离保护，但 PostgreSQL 的表所有者、超级用户等存在绕过边界，仍需正确设计应用身份和查询范围。[PostgreSQL 行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。

阶段建议：先验证 OIDC、一个 LDAP 桥接场景和一个飞书身份／组织接入场景；采用 casbin-rs 作为授权首选候选，不同时引入多套权限引擎。

## 3. 安全与审计

### 推荐路线：策略由我们执行，检测能力可替换

ZenRouter 的 Rust 核心统一选择策略、调用检测器、执行放行／脱敏／拦截，并记录策略和检测器版本。确定性规则可在本地执行；敏感信息识别、语义风险与企业已有 DLP 服务通过接口接入。同步检查服务于当次调用，异步分析服务于历史复盘，两者共享证据但不混淆结果。

| 选择 | 适合解决的问题 | 主要限制 | 当前取舍 |
| --- | --- | --- | --- |
| Rust 本地规则与校验 | 关键词、格式、工具参数约束、可明确表达的企业规则 | 语义理解有限；规则覆盖需要持续维护 | 基础能力，由 ZenRouter 管理规则和版本 |
| Presidio | Python 敏感信息识别与去标识化；可扩展识别器和模型 | 默认以英语模型和识别器为主；中文与行业实体需适配评测，不能保证检出全部敏感信息 | 作为敏感信息检测首选验证对象，可独立部署 |
| NeMo Guardrails 开源库 | 可编程输入、输出等检查，支持自定义动作与模型检测 | 增加 Python／模型依赖；其流程与协议包装可能超出我们需要的范围 | 作为复杂检测和组合能力的候选，不替代 ZenRouter 全部调用控制 |
| 企业现有检测服务 | 接入企业已经维护的规则、分类器和 DLP 能力 | 延迟、可用性、数据传出范围与授权取决于部署 | 保留连接器，按企业环境选择 |

来源：[Presidio 能力](https://presidio.dataprivacystack.org/)、[多语言要求](https://presidio.dataprivacystack.org/analyzer/languages/)、[NeMo Guardrails 开源库](https://docs.nvidia.com/nemo/guardrails/about-nemo-guardrails-library/overview)。本轮未评测中文识别率、误报率、提示注入识别能力或检测延迟；不能把接入检测器表述为已经完成安全保障。

流式内容需要明确检查与释放顺序。NeMo 文档区分“先输出再检查”和“检查后输出”，前者检测到风险时内容可能已经被用户看到；后者增加等待时间，且仍受检测器和窗口范围限制。我们应按业务策略选择，并验证跨片段内容、工具参数、不同协议事件和中途失败，不承诺零延迟下完整拦截。[输出流检查顺序](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/yaml-schema/streaming/output-rail-streaming)。

### 留存与复盘的存储组合

| 层次 | 默认建议 | 演进条件与边界 |
| --- | --- | --- |
| 接收记录、请求索引、风险事件、管理审计 | PostgreSQL，按权限查询并保留变更记录 | 与长正文分离；业务事件和待处理任务可在同一数据库事务内写入 |
| 请求／响应正文、流式归档、附件引用 | 企业掌控的 S3 兼容对象存储，配置加密、访问和生命周期 | 具体产品按企业现有设施选；兼容 S3 不代表具备同等版本、保留锁和恢复能力 |
| 复核、历史重扫、导出和费用汇总 | 可靠后台任务，首期可用 PostgreSQL 任务表／outbox | 积压和吞吐达到门槛后，再比较专用队列或 CDC；不把内存任务视为可靠留存 |
| 大规模聚合分析 | 先用 PostgreSQL 索引与汇总，ClickHouse 作为扩展 | 分析结果可以有延迟，不能替代权威审计事实和额度账本 |

Outbox 模式用于减少数据库状态与待分发事件的不一致，可先以数据库轮询实现；Debezium 是后续 CDC 的一种选择，当前不因此强制引入 Kafka。数据库与对象存储之间仍需补写、核对和恢复机制，outbox 不会自动产生跨存储事务。[Outbox 模式](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)。

只可靠保存请求编号，不等于正文已完整保存。强留痕链路需要可靠保存接收证据和适用正文后再调用上游；流式输出还应明确持久化与向客户端释放的顺序，以及异常时可接受的丢失边界。存储失败、超出接收限制、断流和未知状态必须可见，不能一律显示成功。

调用留痕、管理操作审计与运行观测分开：审计覆盖成功、拒绝、失败、取消、重试及原文访问；观测链路可采样，不能据此声称已全量记录。[OpenTelemetry 采样语义](https://opentelemetry.io/docs/concepts/sampling/)。

正文原文、脱敏副本、索引、导出与备份采用一致的数据生命周期，访问令牌与供应商密钥不作为正文归档。需要防删改保留时，另行评估 Object Lock／WORM；普通数据库追加写入并不等同于存储管理员也无法修改。Object Lock 对版本和保留期有明确要求，并非任何 S3 兼容存储天然具备。[S3 Object Lock 能力定义](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)。

阶段建议：先建立可恢复的留痕和复盘基础，接入基础规则与一个敏感信息检测器；复杂语义检测、全文检索集群及大规模分析引擎按需求扩展。

## 4. 额度与成本

### 推荐路线：PostgreSQL 权威账本，自建层级额度业务

额度业务由 Rust 服务实现，PostgreSQL 保存拨款、占用、消费、释放与调整的权威记录。调用前通过短事务完成额度检查和预占，调用结束后结算；不在整个模型生成期间持有数据库事务或锁。金额采用明确精度的十进制或定点整数，避免二进制浮点累计误差。[PostgreSQL 锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[精确数值](https://www.postgresql.org/docs/current/datatype-numeric.html)。

数据库提供事务基础，不会自动实现完整账本。仍需保证层级约束、稳定的并发控制顺序、幂等和失败恢复；采用更严格隔离时也要处理事务重试。报告中的账本是内部额度与费用记录，不扩展为支付、充值或对外模型转售系统。

### 技术选择比较

| 选择 | 可复用能力 | 主要代价或限制 | 当前取舍 |
| --- | --- | --- | --- |
| Rust + PostgreSQL | 原子事务、精确金额、约束、业务查询与恢复基础 | 热门部门账户可能产生锁竞争，需实际压测 | 首期权威账本建议 |
| Valkey 计数与脚本 | 热数据、共享限流、原子计数 | 异步复制与故障切换存在已确认写入丢失边界 | 可加速，不单独承担权威余额 |
| TigerBeetle | 专用交易数据库；预占、结转、撤销；已有官方 Rust 客户端 | 增加数据库与业务元数据协调；部署和查询能力需单独评估 | 交易吞吐成为瓶颈后再比较 |
| OpenMeter | 基于事件的用量归集和计费能力，适合多维用量分析 | 引入 Kafka、ClickHouse、PostgreSQL 等体系；去重与异步处理需配置 | 后续计量扩展参照，不能仅凭用量统计替代逐级硬额度控制 |
| ClickHouse | 大量费用事件的分析与聚合 | 合并去重是异步过程，普通查询可能暂见重复记录 | 分析库候选，不能直接作为扣费和幂等依据 |

Valkey 官方明确指出异步复制及同步确认命令不等同于强一致系统；TigerBeetle 提供 pending／post／void 等交易状态；OpenMeter 当前架构把异步用量与事务业务状态分开；ClickHouse 的 ReplacingMergeTree 不保证后台合并前已经去重。[Valkey 复制边界](https://valkey.io/topics/replication/)、[TigerBeetle 两阶段交易](https://docs.tigerbeetle.com/coding/two-phase-transfers/)、[Rust 客户端](https://docs.tigerbeetle.com/coding/clients/rust/)、[OpenMeter 架构](https://openmeter.io/docs/open-source/architecture)、[ClickHouse 去重边界](https://clickhouse.com/docs/concepts/features/operations/update/replacing-merge-tree)。

### 内部额度与外部供应商分别建账

| 口径 | 建议表达 | 需要避免的混淆 |
| --- | --- | --- |
| 组织内部额度 | 公司分配部门，部门在授权范围内再分配员工；记录周期、未分配、占用与消费 | 下发额度不是已经发生费用；向上汇总不能再次累加成多份支出 |
| 实际调用成本 | 归集每次真实上游尝试的用量，关联价格版本、币种和归属 | 一次逻辑请求可能有多次收费尝试；失败不等于免费 |
| 供应商每日消耗 | 按供应商、账号、模型、业务日期聚合；区分估算、已结算与待对账 | 网关统计与供应商账单可能有折扣、舍入、返还、时区和延迟差异 |
| 供应商余额与外部限额 | 若供应商提供接口则读取，否则保留人工登记或未知状态；分别管理 RPM／TPM 等配额 | 累计消耗不是余额；多个网关实例不会增加上游总配额 |

例如 A 部门本周获分配 10,000 美元额度，再给员工分配 2,000 美元：这是部门额度内部的分配，不新增 2,000 美元成本。员工消费 100 美元后，员工与部门报表都可展示这笔归属，但企业总消费只记一次。该例只解释记账口径，具体共享池、回收及跨周期规则留待模块细化。

### 一致性与真实计费边界

所有网关实例共享权威额度状态，不能把同一笔可用余额复制到各实例分别消耗。权限委派决定谁能分配，账本事务决定是否真的分得出去；多层余额与消费必须在同一规则下保持一致。

预占估算本身不能保证绝不超额。严格额度需要可约束的调用成本上界，例如受支持的价格规则和最大输出；无法估价的调用应明确拒绝或进入单独风险策略。上游用量未知时不能按零结算，也不能仅因超时就无条件释放可能已经发生费用的占用。

保留供应商原始计量与价格版本，分别识别输入、输出、缓存等可获取用量，缺失项显示未知。缓存命中、重试、退款和修正通过可追溯事件体现；历史费用不应随今日价格变化而被静默重算。周／日额度的时区、重置时点与跨周期占用归属在后续设计中明确。

阶段建议：先实现可验证的层级账本与基础成本归集，保留供应商对账入口；不提前引入完整订阅计费平台或专用交易数据库。

## 5. 三个模块的共同技术基线

| 部位 | 建议 | 引入边界 |
| --- | --- | --- |
| 自有业务核心 | Rust，先按模块组织代码和数据职责 | 不因有三个业务模块就强制拆成三个微服务 |
| 事务数据 | PostgreSQL | 统一部署可减少初期运维；身份、审计与额度仍有明确数据所有权和权限 |
| 正文留存 | S3 兼容对象存储接口 | 企业已有存储优先；具体实现、版本保留和加密能力单独核对 |
| 热缓存与共享限流 | Valkey 按需要接入 | 不成为唯一账本或唯一审计存储 |
| 企业身份桥接 | 已有 SSO 优先，Keycloak 可选 | 不能由身份组件直接决定全部业务权限 |
| 检测器 | Rust 本地规则 + 可选 Python／HTTP 服务 | Presidio、NeMo 或企业服务各有能力边界，按需要启用 |
| 后台处理与分析 | 可靠任务和 outbox 起步，分析库后置 | 先测积压、恢复、查询和资源竞争，再决定是否增加队列、CDC 或 ClickHouse |

三个模块共享身份与组织标识、请求与尝试关联、策略版本和时间口径。组织权限管理授权范围，额度模块管理金额约束，安全审计记录事实和复核结论；任何模块都不通过直接改写其他模块数据来绕过其规则。

平台管理与运维仍作为横向能力，覆盖配置发布、密钥管理、指标告警、备份恢复和多实例部署。本轮不把它扩展为第五个一级业务模块。

## 6. 开源许可与可交付性

## 7. 后续最小验证与待定信息

| 模块 | 后续验证重点 | 通过后才能确认 |
| --- | --- | --- |
| 组织与权限 | OIDC／LDAP／飞书接入；跨部门越权；离职撤权；原文与导出权限；多实例策略更新 | 连接器范围、授权引擎与权限生效时限 |
| 安全与审计 | 中文与业务敏感信息样本；流式跨片段检测；存储中断、恢复及重放；正文访问与到期清理 | 检测器组合、流式处置模式、留存完整性和容量 |
| 额度与成本 | 多实例同时花同一部门余额；重试和重复结算；跨周期占用；未知用量与供应商差异 | 并发约束、账本恢复和费用口径 |

运行验证、性能压测和故障注入均未执行。尤其不能凭数据库或组件文档直接承诺高并发下零超额、零审计丢失、即时撤权或全部风险可检出。

当前缺少的输入是：首批企业身份源、组织规模、峰值并发与长流比例、正文日增量及保留期、可接受检测延迟、严格额度覆盖范围、供应商账单能力、可用性和恢复目标。它们不妨碍形成上述路线，但决定最终版本、部署规模和哪些可选组件需要提前引入。

本轮交付到此收敛：三个模块都有默认路线、替代方案和验证门槛。下一步统一评审四大模块的技术基线，再按模块细化；暂不安装组件、不开始生产实现，也不继续扩大网关专项。
