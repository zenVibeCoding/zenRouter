阶段安排：网关选型保留路线摘要，其他三个模块的初步技术调研已完成，见[组织、审计与额度调研报告](governance-research.html)。下一步统一评审四模块基线，补充规模、部署和恢复目标，再按模块细化和验证；网关专项深入验证继续后置。

| 本轮补充模块 | 初步技术建议 |
| --- | --- |
| 组织与权限 | OIDC 与可选 Keycloak 桥接，casbin-rs 作为授权首选候选；组织、角色范围和撤权由 ZenRouter 管理 |
| 安全与审计 | Rust 策略执行、可替换检测器，PostgreSQL + 对象存储可靠留存；Presidio 优先验证，分析库按需引入 |
| 额度与成本 | Rust 自建层级额度业务，PostgreSQL 权威账本；Valkey 不单独承担余额，供应商消耗与真实余额分别表达 |

建议采用 **自建 ZenRouter Rust 网关与治理核心，封装 LiteLLM Python Core SDK 复用模型适配** 的路线。Rust 原生组件在限定协议链路通过验证后逐步引入。完整 LiteLLM Proxy 作为验证基线，agentgateway、Bifrost 与其他网关保留为参照；产品的对外 API、配置、路由策略与治理数据由 ZenRouter 掌握。

Rust 是首选，Python 可用于复用成熟适配，不要求统一语言。最新固定版本源码结论见[LiteLLM Rust 与复用专项](litellm-reuse-research.html)；各完整网关的调用能力、技术栈和模型范围继续保存在[网关比较](gateway-research.html)。完整 Proxy、Python SDK 和 Rust 组件的能力须分别验证。

这是一项基于当前需求、官方资料及局部源码核查的工程建议，不是性能测试结论。团队经验、实际流量和首批供应商尚未明确，因此推荐保留可替换的数据面边界；通过验证门槛后再锁定底座、稳定版本和具体依赖。

本轮完成：原五个候选的官方资料与仓库许可检查、LiteLLM 与 Bifrost 的关键源码核查，并补查三个 Rust 候选的状态与声明，四模块能力映射、总体架构、技术栈建议及验证方案。**未部署运行候选网关，未调用真实供应商，未执行性能、故障注入或多副本预算测试。** 下文“支持”指文档或源码存在对应能力，不能视为 ZenRouter 验收已通过。

多协议补充结论：下游自主选择接口，平台同时提供同协议代理与跨协议转换。agentgateway 当前矩阵尚未实现 Anthropic 上游的 Responses 接入；LiteLLM 与 Bifrost 有对应转换文档。该差异须进入选型门槛，详见[网关协议专项](gateway-research.html#section-8)。

## 2. 选型依据与假设

| 依据 | 对技术选择的影响 |
| --- | --- |
| 开源、企业自行部署 | 必须区分社区能力、商业许可模块与外部云服务依赖 |
| 组织与权限 | 身份接入可复用，企业内部的资源权限与数据范围由 ZenRouter 管理 |
| 安全与审计 | 同步风控、全量请求响应留存、周期复盘需要统一证据与可靠写入 |
| 模型与路由 | 同时提供 OpenAI、Anthropic、Gemini 接口供下游选择；同协议代理、跨协议转换、流式与工具调用、同模型跨渠道切换是底座重点 |
| 额度与成本 | 部门到员工逐级分配、并发预占、费用归属不能仅以单密钥限额代替 |
| 平台管理与运维 | 配置发布、故障恢复、记录积压和策略有效状态必须可观测 |

调研暂按“企业私有部署优先、首批文本／流式／工具调用、小范围试点后扩展”比较方案。调用量、正文大小、保留期限、组织规模、可用性目标、团队主语言均为未知；不据此虚构服务器数量、吞吐指标、工期或成本报价。企业私有部署与对外托管多租户是不同交付问题，后者尚未确定。

筛选顺序：先看开源可交付、协议保真和治理扩展点，再看可靠性、维护成本及运维复杂度；性能宣传、模型数量和仓库星标不直接作为排名依据。

### 三条实施路线

| 路线 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| 直接深度修改现有网关与控制台 | 早期页面和配置复用较多 | 与原项目数据模型、企业版边界和升级紧密耦合 | 不作为默认路线 |
| 自建网关与治理，复用模型适配核心 | 保留协议适配成果，掌握入口、路由、组织、额度和证据 | 需封装 SDK、稳定内部接口并验证流式和治理行为 | 推荐，Rust 优先且允许 Python |
| 全栈自研 | 行为和许可组合自主性高 | 长期维护模型协议、流式边界与错误差异，首期工作量最大 | 候选均无法通过关键门槛时再考虑 |

## 4. 四大模块怎样复用

| ZenRouter 模块 | 建议复用 | 需要掌握的业务能力 |
| --- | --- | --- |
| 组织与权限 | 标准身份协议、现有企业 IdP；可选 Keycloak 桥接 LDAP／AD | 组织项目应用归属、角色作用范围、模型授权、员工身份绑定和撤权联动 |
| 安全与审计 | 网关输入输出扩展点、检测器接口、标准观测采集 | 策略版本与强制执行、可靠接收记录、正文生命周期、管理审计、周期复盘与风险处理 |
| 模型与路由 | 供应商适配、用量解析、流式处理、重试回退和基础缓存 | 业务模型目录、候选能力与约束、渠道配置发布、统一解释和质量评测 |
| 额度与成本 | 上游用量和基础价格数据，可验证后复用计量组件 | 逐级拨款、额度回收调整、统一预占结算、层级约束、内部归因和供应商对账 |

一个重要原则：**同一类规则确定一个权威来源。** 部门额度账目由 ZenRouter 持有，网关消费其授权或预算决策；若保留底座限额，应明确它只是技术护栏或一致的镜像配置。不能让两套不同步的预算引擎各自扣费、各自判断剩余额度。

## 5. 五项关键技术发现

### 5.1 同模型切换可复用，但必须验证执行边界

LiteLLM 文档区分同一模型组内的部署重试与模型组间的 fallback；Bifrost 提供供应商重试与回退链。两者具备实现“同模型、不同渠道”的基础。需要实际验证协议参数、工具调用、上下文与流式输出，而不是只验证返回成功。来源：[LiteLLM 请求链路](https://docs.litellm.ai/docs/proxy/architecture)、[Bifrost 回退机制](https://docs.getbifrost.ai/features/retries-and-fallbacks)。

工程判断：ZenRouter 的安全阻断应作为终止决策，不能被底座自动换渠道绕过；每次额外尝试都要重新满足候选约束并记录费用。已输出内容后的故障不应通过拼接另一份生成结果掩盖。第三方渠道的模型名称相同，也不代表实际版本和能力已验证一致。

### 5.2 缓存管理与缓存观测是两条能力

LiteLLM 提供响应缓存并单独引用上游提示词缓存；Higress 的 AI Cache 文档包含流式与非流式结果缓存。来源：[LiteLLM 缓存](https://docs.litellm.ai/docs/proxy/caching)、[Higress AI Cache](https://higress.io/en/docs/latest/plugins/ai/api-provider/ai-cache/)。

建议先记录供应商缓存读取／写入用量及原始计量，再按业务显式启用网关精确回答缓存。跨供应商统一显示不能强行统一计费公式；缺失信息显示未知。语义缓存后置验证，避免把“问题相近”直接当作可复用回答的依据。缓存命中仍需服从当前权限与安全策略。

### 5.3 普通日志尚不足以满足全量可靠留痕

LiteLLM 架构资料描述响应后的异步日志处理。Bifrost 固定提交的日志插件中，调用前钩子使用内存数据与异步写入设计，源码明确未在该钩子内进行数据库写入。来源：[LiteLLM 架构](https://docs.litellm.ai/docs/proxy/architecture)、[Bifrost 日志源码](https://github.com/maximhq/bifrost/blob/d3f3f942296886e2297868de1b580aab26f4d8a2/plugins/logging/main.go#L1880)。

工程结论：不能直接把默认调用日志当作“接收记录持久化成功后才发往上游”的保证。ZenRouter 需要可靠接收凭证、请求与尝试关联、结果补写、异常恢复和积压监控。权限拒绝、策略短路、缓存命中与断流也要覆盖；只有成功回调不足以证明全量。

建议把元数据／索引与大正文分开：前者用于定位和聚合，后者存储于企业掌控的对象存储，并通过授权入口访问。可观测链路可采样，业务审计留痕不能依赖采样。

### 5.4 有预算预占，仍不等于有部门逐级拨款

LiteLLM 当前预算文档已描述默认预占、结算与严格失败策略；本次源码核查确认存在预占实现，同时在无法估价或非正价格等分支跳过预占。团队密钥与个人预算的适用关系也有专门规则。来源：[预算说明](https://docs.litellm.ai/docs/proxy/users)、[固定提交源码](https://github.com/BerriAI/litellm/blob/b25ea48c4b194dbae4d858839619c426f1258ac6/litellm/proxy/spend_tracking/budget_reservation.py#L232)。

Bifrost 提供多维预算配置；本次没有证明其社区版在所有目标场景下具备跨副本、全部祖先额度的原子预占，不能仅凭“层级预算”描述认定满足。来源：[Bifrost 预算](https://docs.getbifrost.ai/features/governance/budget-and-limits)。

建议将逐级额度分配作为 ZenRouter 自有业务模型。分配不算消费，消费向上汇总不重复扣计；预占、结算、释放与对账使用同一权威账目。并发控制必须用实际故障和重试场景验证，不能通过正常单请求演示验收。

### 5.5 实时风控可通过扩展点落地，检测质量仍需独立评估

LiteLLM 有自定义 guardrail 接口；Bifrost 有调用前后及流式处理插件扩展；Higress 有脱敏和内容安全插件。来源：[LiteLLM 自定义风控](https://docs.litellm.ai/docs/proxy/guardrails/custom_guardrail)、[Bifrost 插件](https://docs.getbifrost.ai/plugins/getting-started)、[Higress 插件目录](https://higress.ai/en/plugins/)。

建议自有策略与证据模型，检测器按接口接入。规则、密钥识别、内容分类各自解决不同问题；接入一个检测器不代表能识别所有风险。需比较请求前、响应释放前和流式分段的执行能力，确保检测超时有明确行为。异步分析用于复盘，不承担已经发送内容的同步阻断。

## 6. 推荐总体架构

建议首期采用“模块化控制面 + 自有 Rust 网关 + 内部模型适配组件 + 异步分析任务”。四个业务模块先按代码和数据职责划分，不要求部署成四组微服务；Python 适配组件可先作为网关旁的独立进程部署。

| 层 | 职责 | 推荐边界 |
| --- | --- | --- |
| ZenRouter 控制台与管理 API | 四大模块、平台管理与运维 | 统一业务对象、授权、额度账目和配置版本 |
| 自有 Rust 网关 | 协议入口、可信身份、可靠接收、预算和内容策略、路由决策 | 覆盖全部对外入口与每次尝试；统一掌握重试和渠道切换 |
| 模型适配组件 | 协议转换、流式和上游调用 | 优先封装 LiteLLM Python Core SDK；Rust 原生组件按能力逐步替换 |
| 数据与分析 | 正文留存、事件处理、风险复盘、费用汇总 | 先持久化必要证据，再异步补齐分析；失败可重放与去重 |

网关多实例入口负载均衡、横向扩容及高可用已进入核心范围。入口分流与上游模型渠道分流分别设计；全局额度、限流、配置、长连接排空和共享依赖容量需一起验证。具体候选部署差异见[网关专项](gateway-research.html#section-7)。

控制面通过版本化配置影响数据面，数据面输出统一请求、尝试、用量与风险事件。控制面不可用时的缓存配置有效期、撤权和预算行为列入验证；不先承诺任意时长离线自治。

不建议只在网关外增加一次检查就认为治理完成：内部重试、缓存、输出流和工具参数可能需要底座插件协作。强留痕和预算检查带来的额外延迟应计入真实性能测试。

## 7. 技术栈建议

下表是默认候选组合，不代表已经锁定版本。版本选择以 PoC 时的受维护稳定版本、依赖许可与部署验证为准；本轮开发分支快照只用于证据定位。

| 部位 | 默认建议 | 选择理由与约束 |
| --- | --- | --- |
| 管理控制台 | React + TypeScript + Vite | 独立 SPA，适合管理型界面；若团队已有 Vue 标准可等价替换，不以 UI 框架决定网关底座 |
| 业务控制面 | Rust，模块化单体；Tokio／Axum／Tower 候选 | 纳入用户语言偏好；以团队维护能力与验证结果确定。前端和外部网关无需强制同语言 |
| 网关与模型适配 | Rust 自有网关 + LiteLLM Python Core SDK 适配组件 | 先验证 SDK 的多协议与流式；原生 Rust 组件做限定链路实验，完整 Proxy 仅作参照 |
| 权限／额度／配置／必要事件 | PostgreSQL | 事务和行锁可作为一致性实现基础；应用仍须设计幂等、锁顺序和恢复 |
| 热缓存／限流 | Valkey 候选 | 用于可重建热数据与计数；与底座 Redis 接口和脚本兼容性需测，不作为唯一财务账本 |
| 请求响应正文 | S3 兼容对象存储接口 | 选择企业已有存储或可自行部署的实现；具体产品与许可证待部署约束确定 |
| 身份接入 | 标准 OIDC，Keycloak 可选桥接 | Keycloak 支持 LDAP／AD 联邦及身份代理；无需每家企业强制增加一个身份服务，飞书需单独验证适配 |
| 业务授权 | casbin-rs 首选候选，Cedar／OpenFGA 作为不同复杂度的替代 | 组织层级与数据作用范围由 ZenRouter 定义，登录和目录同步不自动完成授权 |
| 安全检测 | Rust 本地规则 + 可替换检测器，Presidio 优先验证 | Python 检测服务可选；中文识别、流式检查顺序和模型许可单独核对 |
| 异步任务 | PostgreSQL 持久化任务／outbox 起步 | 优先减少基础设施种类；在队列吞吐和故障恢复验证不足时再引入专用持久化消息系统 |
| 分析查询 | 先 PostgreSQL 索引与汇总；ClickHouse 可选 | 大规模跨调用聚合的候选，不提前作为所有部署必需项；不取代事务账本 |
| 运行观测与部署 | OpenTelemetry、Prometheus；容器部署，按需 Helm | 运行观测与审计存储职责分开；多副本一致性必须实际验证 |

官方能力依据：[PostgreSQL 锁与并发](https://www.postgresql.org/docs/current/explicit-locking.html)、[Valkey 事务](https://valkey.io/topics/transactions/)、[Keycloak 管理文档](https://www.keycloak.org/docs/latest/server_admin/index.html)、[ClickHouse 分析定位](https://clickhouse.com/docs/get-started/about/intro)、[OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/)。授权、检测与账本方案的证据及边界见[三模块调研](governance-research.html)。组合与取舍为本次建议，并不意味着这些组件天然组成完整可靠系统。

初期暂不强制加入向量数据库、全文检索集群、Kafka 或服务网格。正文检索需求、语义缓存及事件吞吐达到明确门槛后再评估。容量估算用“每日请求数 × 平均正文大小 × 保留天数”，另外计算索引、备份、副本和重试；目前没有足够输入给出容量结论。

## 8. 验证门槛与最小实验

以下实验均为下一阶段待执行，不是本轮测试结果。先用可控模拟上游验证网关行为，再用获准的真实供应商和测试数据确认兼容性；模拟上游不能证明真实缓存、定价和模型质量。

| 实验 | 方法 | 通过依据 |
| --- | --- | --- |
| 同模型双渠道切换 | 主渠道返回超时、限流、服务错误，备用渠道正常；另设安全拒绝场景 | 获准场景切换成功，安全拒绝不被绕过；尝试链、超时总预算和费用记录完整 |
| 协议与流式 | 三类客户端入口；同一 Anthropic 上游的 OpenAI Chat 转换和 Anthropic 同协议调用，Responses 另项核对；工具、结构化输出及流式异常 | 参数保真、终态明确，不把两份生成拼接为成功响应 |
| 可靠记录 | 接收后、调用中、结果返回前分别终止进程；模拟存储不可用 | 已接受记录可恢复，未知状态可见；强留痕入口在持久化失败时不发起新上游调用 |
| 预算并发 | 两个网关副本同时逼近员工与部门额度，注入超时、重复事件和重启 | 符合约定容差，无重复结算，释放与待对账可追溯；所有适用上级约束有效 |
| 缓存口径 | 重复请求、跨权限范围、策略更新、渠道切换、用量字段缺失 | 缓存隔离和失效正确；区分网关命中和上游缓存；未知用量不归零 |
| 身份与权限 | 外部身份登录、组织变更、离职撤权、应用代表员工调用 | 可信归属可映射；敏感原文和管理权限按范围执行；撤权满足确认的时效 |
| 实时风控 | 输入／输出／工具参数命中，检测器超时，流式跨段样本 | 正确执行策略并留下证据；未检测不显示安全；已释放内容范围准确 |
| 性能与扩展 | 相同机器、相同模拟上游、相同日志和风控配置；分级并发与长流式请求，验证多实例扩缩容、故障摘除和滚动升级 | 输出吞吐、错误率、首 Token、P95/P99、资源与积压曲线；不引用厂商异构基准做胜负结论 |

先选受维护稳定版本并记录镜像摘要；开发分支不直接用于生产。底座通过上述关键能力后，再开展四模块详细功能设计；遇到缺口先比较插件／适配成本，再决定更换候选或有限修改上游。
